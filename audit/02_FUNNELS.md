# ФАЗА 2 — Воронки: від кліку по рекламі до оплати й повернення

> Аудит read-only. Кожна знахідка = `файл:рядок` + цитата/крок. Пріоритети P0–P3.
> Гроші-вплив і фікс — для P0/P1.

## 0. Контекст, який змінює всю оптику

Sixtio — **Telegram Mini App**, не веб-сайт і не застосунок зі стору. З цього випливає
три речі, які вбивають половину класичного чек-листа воронок (і це переважно **на користь**):

- **Немає email/OAuth/пароля.** Автентифікація — Telegram `initData` (HMAC-підпис).
  Отже: немає підтвердження email, скидання пароля, magic link, «логіну з іншого
  пристрою», виходу. Цілий клас витоків воронки **фізично відсутній** — це сильний плюс.
  Доказ: `api/_lib/telegram.js:9` `validateInitData`, всі `api/*.js` автентифікують лише через `initData`.
- **Немає app-store / deferred deep link.** Mini App відкривається миттєво в Telegram,
  без встановлення. Пункт «клік → стор → інсталл → чи туди потрапив» **не застосовний**.
- **Класичні `fbclid/gclid/ttclid` у застосунок не долітають** (див. Воронку А, P1).

## 2. Воронка А — вхід із реклами → атрибуція

| Крок | Файл | Що може зламатись | Що бачить користувач |
|---|---|---|---|
| Клік по рекламі → `t.me/Sixtiobot?start=SRC` | Telegram | payload > 64 симв. або не `[A-Za-z0-9_-]` → відкидається як «organic» (`sources.js:14` `SOURCE_RE`) | нічого; але атрибуція втрачена |
| `/start SRC` долітає у webhook | `analytics.js:186-193` | — | Welcome-повідомлення бота |
| Стейджинг джерела | `sources.js:65` `stashPendingSource` (insert-only, перше джерело виграє) | best-effort, не кидає у webhook | — |
| Вхід через Mini App `?startapp=SRC` | `telegram.js:42` `getStartParam` (HMAC-підписаний start_param) | — (довірено) | — |
| Застосування при реєстрації | `sources.js:113` `applySourceOnRegistration` (пише `users.source` лише коли NULL) | — | — |
| Агрегація для `/stats_sources` | `sources.js:172` `sourceStats` → RPC `source_stats` | clicks недораховуються (ВИТІК-2) | лише власник у боті |

**🔴 ВИТІК-1 (P1) — click-id не переживає вхід у застосунок.**
`SOURCE_RE = /^[A-Za-z0-9_-]{1,64}$/` (`sources.js:14`). Meta `fbclid` (~100+ симв.),
Google `gclid` (~90 симв.), TikTok `ttclid` — **довші за 64 і/або містять неприпустимі
символи → відкидаються**. Telegram deep-link payload у принципі один короткий токен,
не URL з query. Наслідок:
- Немає per-click атрибуції → **неможливо** побудувати Conversions API (Meta CAPI),
  offline-conversion upload (Google), Events API (TikTok), прив'язані до конкретного кліку.
- Рекламні кабінети оптимізуються **наосліп**: без сигналу «цей клік → реєстрація/оплата»
  алгоритми Meta/Google/TikTok не можуть навчати lookalike/retargeting на конверсії.
- Максимум, що є — **кампанієвий** бакет (`?start=tgads1`) через `source_stats`.

**Гроші-вплив:** прямий. Оптимізація на кампанієвому рівні без click-level сигналу
= 2–5× гірший CAC на платному трафіку Meta/Google/TikTok. На бюджеті це найдорожча діра фази.
**Фікс (~1–2 дні):** ввести короткий `cid` (свій 8–12-символьний ідентифікатор кліку),
який (а) генерується на проміжному лендингу/редіректорі перед `t.me/...?start=cid_XXXX`,
(б) на бекенді мапиться назад на `fbclid/gclid` через окрему таблицю, (в) на подіях
`registration`/`purchase` вивантажується у CAPI/GAds/TikTok. Тобто короткий токен —
це не джерело, а **ключ** до збереженого повного click-id. Потребує проміжного редіректора
(бо сам Telegram не пропустить довгий click-id).

**⚠️ ВИТІК-2 (P2) — вхід через `?startapp=` не рахується як клік.**
Подія «start» (верх воронки) і «клік» для `source_stats` пишуться лише на `/start`-webhook
(`analytics.js:190` `trackStart`). Пряме відкриття Mini App через `?startapp=SRC` реєстрацію
атрибутує (`applySourceOnRegistration` через start_param), але webhook `/start` **не шле** →
`trackStart` не спрацьовує → `clicks` у `source_stats` недораховуються →
`completionRate = registrations/clicks` спотворений (може бути >100%).
**Гроші-вплив:** непрямий — ти приймаєш рішення по бюджету на кривих цифрах.
**Фікс (~2 год):** писати подію `start` також при першій реєстрації через start_param
(у `applySourceOnRegistration`/`profile.js`), або рахувати «clicks» з `signup_sources`, а не з webhook-подій.
*(Точну поведінку Telegram щодо `/start` при `?startapp=` — див. НЕ ЗМІГ ПЕРЕВІРИТИ #1.)*

## 3. Воронка Б — онбординг

| Крок | Файл | Що може зламатись | Що бачить користувач |
|---|---|---|---|
| Старт онбордингу | `onboarding.html:811-829` init | якщо `me.profile` є → `replace('matches.html')` | одразу matches |
| profile stage (стать/ціль/фото/вік/місто/…) | `onboarding.html:489` `handleProfileText` | вік <18/некоректний → повторний запит (`:493`) | «тобі має бути 18+» |
| Фото | `onboarding.html:539-576` → `/api/photo` | NSFW-422 → повторний запит фото; інша помилка → пропуск | «фото відхилено» / далі |
| Місто | `onboarding.html:461-477` (geo/Nominatim) | зовнішній Nominatim падає → ручне введення | fallback на ручний ввід ✓ |
| submit профілю | `onboarding.html:512` `/api/profile-info` (**один раз, у кінці profile stage**) | падіння → `console.error`, але **йде далі** у psych (`:526`) | непомітно |
| psych stage | `onboarding.html:607-666` → `/api/answer` (інкрементально) | таймаут 25 c (AbortController `:232`); падіння → відповідь лишається лише в localStorage, діалог не блокується (`:661`) | без збою продовжує |
| finish → Twin | `onboarding.html:744` `/api/profile` (до ~10 c) | падіння → fallback-картка (`:761`) | «дякую» + кнопка «Продовжити» |
| traits | `onboarding.html:753` `/api/analyze-traits` fire-and-forget | — | заповнюється згодом ✓ |

**🔴 ВИТІК-3 (P1) — немає resume: закрив → рестарт з нуля.**
`STORAGE_KEY = 'sixtio_onboarding_answers'` **пишеться** (`onboarding.html:633`),
але у файлі **немає жодного `getItem(STORAGE_KEY)`** — чернетку ніколи не читають назад
(перевірено grep: єдине входження — оголошення на `:207`). Логіка старту (`:811-829`):
`/api/me` → якщо `me.profile` відсутній → `askNextProfile()` від `pIndex=0`.
- Twin (`profiles`-рядок) створюється **лише** у finish() → `/api/profile`. Доти `me.profile`
  = null → онбординг щоразу починається з **profile stage від першого кроку**.
- `profile-info` (стать/вік/ціль/інтереси/цінності/біо) відправляється **одним запитом
  наприкінці** profile stage → якщо юзер відпав під час profile stage, ці дані взагалі не збережені.
- psych-відповіді пішли в `/api/answer` посерверно, але UI все одно **перепитує все заново**.

**Сценарій:** клік з реклами → почав онбординг → на 8-му з 10 психпитань закрив Telegram →
повернувся → бачить **знову стать/фото/вік і всі психпитання спочатку**. Це найтиповіший
патерн платного трафіку (людина відволіклась) і найдорожчий: заплатив за клік, юзер майже
дійшов — і мусить усе повторити.
**Гроші-вплив:** прямий і великий. Онбординг тут довгий (≈9 профіль-кроків + N психпитань,
кожне — окремий AI round-trip). Кинути на середині й побачити рестарт = висока ймовірність
не повернутись. Це головний leak воронки активації.
**Фікс (~0.5–1 день):** (1) читати `STORAGE_KEY` на старті й відновлювати `answers`/`index`;
(2) або серверний resume — `/api/me` повертає `onboardingProgress` (скільки psych-відповідей
уже є) і UI пропускає їх; (3) `profile-info` слати інкрементально, а не одним пакетом у кінці.

**Спостереження (не баг):** у profile/psych **немає кнопки «назад»** — чат-стиль, попередню
відповідь не виправити під час флоу (лише пізніше через редагування профілю). Прийнятно для
чат-онбордингу, але варто мати на увазі для копірайтингу («відповідай уважно»).

## 4. Воронка В — активація до ключової дії

| Крок | Файл | Найдовша пауза | Ризик |
|---|---|---|---|
| Welcome → returning-check | `index.html:111` `/api/me` | — | offline → лишається на welcome ✓ |
| Онбординг | §3 | **Twin-генерація ~10 c** (finish `/api/profile`) | найдовша пауза всього флоу |
| matches | `matches.html` | — | порожньо → CTA ✓ |
| feed → свайп → like → match | `feed.html:544` | — | free-male ліміт → paywall |

Кроків від старту до ключової дії (перший match) багато: welcome → онбординг(9+N) →
matches → feed → свайп → like → взаємний like. **Найдовша одинична пауза** — Twin-генерація
на finish (AI, до Vercel-ліміту 10 c); `analyze-traits` винесено у fire-and-forget (добре,
не блокує). Психпитання — по одному AI round-trip кожне (з followup — два); на повільному
3G це відчутно, але є 25-c таймаут + graceful advance.

| Поповнення Stars | `paywall.js:242-284` `create_stars_invoice` → `openInvoice` | `busy`-guard (`:244`); скасування → no-op (`:276`) | нативний Telegram Stars-лист |
| pre_checkout | `analytics.js:139-143` answer ok:true <10 c | — | — |
| credit | `analytics.js:220` `creditSuccessfulPayment` → ідемпотентно по `charge_id` | **⚠️ див. Фазу 11 SEC-1 (P0): webhook без підпису** | оптимістичний +Stars, звірка з /api/me за 2.5 c |
| Повернення | `paywall.js:230-240` `reconcileDeposit` / `:336` `close` + `onSuccess` | — | un-blur / оновлений баланс ✓ |

**Позитив (сильний):**
- Лист **завжди закривається**, шлях назад у продукт є — **немає** пейвол-глухого-кута.
- Подвійний клік по оплаті захищено `busy`-прапорцем у всіх трьох гілках.
- Back/скасування під час нативного Stars-листа → `status !== 'paid'` → no-op, стан не б'ється.
- «Restore purchases» **не потрібен**: баланс серверно-авторитетний, reconcile з `/api/me`.
- Premium — разовий (`premiumUntil`, не автосписання) → скасовувати нічого.

**⚠️ Прапорець копірайту/легалу (для Фази 32):** Premium — разовий на строк, **не**
автопродовження. Треба явно це проговорити в UI (інакше юзер очікує підписку/скасування).
Це не баг воронки, а очікуваність — прапорець юристу/копірайтингу.

**⚠️ Зв'язок з P0:** платіжний webhook не валідує підпис (Фаза 11, SEC-1). У контексті
воронки це означає: сама оплата працює, але «безкоштовні Stars» через підробку webhook
знецінюють увесь платний шлях. Деталі й фікс — у звіті Фази 11.

## 9. НЕ ЗМІГ ПЕРЕВІРИТИ

1. **Чи шле Telegram `/start` у webhook при вході через `?startapp=SRC`** — *що:* точний
   вплив ВИТІК-2 на `source_stats.clicks`. *чому:* потребує живого Telegram-клієнта й
   бойового бота; локально не відтворити. *як перевірити вручну:* відкрити
   `t.me/Sixtiobot/app?startapp=test1`, подивитися у Vercel-логах, чи спрацював `trackStart`,
   і в БД `analytics_events` подію `start`; порівняти з `signup_sources`.
2. **Клієнтський/серверний ліміт довжини відповіді у психпитанні** — *що:* чи не покладе
   дуже довгий текст `/api/answer`/генерацію Twin. *чому:* не читав `api/answer.js` тіло на
   валідацію довжини в цій фазі. *як перевірити:* надіслати 20k символів у психпитання
   локально (`npm run dev` + ALLOW_FAKE_AUTH), глянути відповідь `/api/answer` і finish.
3. **Реальна конверсія по кроках** — *що:* де фактично найбільший drop-off. *чому:* потрібні
   бойові дані `analytics_events` (`start → onboarding_complete → first_like → …`). *як
   перевірити:* `/stats` у боті власником або SQL по `stats_funnel` (migration 033) після трафіку.
