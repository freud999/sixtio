# ФАЗА 12 — Платіжний шлях (Telegram Stars)

**Метод:** READ-ONLY розбір усього коду оплати: `paywall.js`, `api/interact.js`
(`purchase`, `create_stars_invoice`), `api/chat.js` (вхід вебхука),
`api/_lib/analytics.js` (`handleTelegramUpdate`, `creditSuccessfulPayment`),
`api/_lib/entitlements.js`, міграції 010/017/018/026. Кожна теза — з пруфом.

---

## 0. TL;DR

Платіжна модель — **тільки Telegram Stars (XTR), разові покупки**. Немає підписок,
пробних періодів, тарифів, апгрейдів/даунгрейдів, прорації, карток, 3DS, чарджбеків.
Це різко звужує клас можливих багів — і більша частина «поганих сценаріїв» з ТЗ
**не застосовна за дизайном** (і це добре).

Внутрішня механіка **зроблена акуратно**: списання Stars — атомарні guarded-RPC,
нарахування — ідемпотентне по `telegram_payment_charge_id`, сервер — єдине джерело
істини по ціні й entitlement, крос-девайс безкоштовний.

**АЛЕ є одна діра рівня P0, яка знецінює всю економіку:**
вебхук платежів **не має жодної перевірки підпису** — будь-хто може підробити
`successful_payment` і намайнити собі необмежено Stars безкоштовно. Це той самий
дефект, що вже підсвічувався у Фазі 11; тут він підтверджений саме як **платіжний
блокер №1**. З увімкненою рекламою це = 100% злив і виручки, і рекламного бюджету.

| # | Severity | Проблема |
|---|----------|----------|
| **P12-1** | **P0 BLOCKER** | Вебхук `/api/chat` не перевіряє підпис → підробка `successful_payment` = безкоштовні Stars |
| P12-2 | P2 | Немає обробки refund → рефанд не списує Stars з гаманця (розсинхрон ledger↔гроші) |
| P12-3 | P2 | Втрачений webhook top-up = юзер заплатив, Stars не нараховані, немає шляху відновлення |
| P12-4 | P3 | Лутбокс-виграш «−30% на Premium» ніде не редімиться (обіцянка без реалізації) |
| P12-5 | P3 | Оптимістичний reconcile top-up (2500 мс фіксовано) може показати застарілий баланс |

## 1. Карта платіжного шляху

Є **дві незалежні рейки**, їх легко сплутати:

### Рейка А — внутрішня трата (`op: 'purchase'`)
Списує вже наявні Stars з `users.stars_balance` за premium / swipe_pack / likes_pass.
**Не торкається платежів Telegram.** Гроші вже в гаманці.
- `paywall.js:286-343` → `POST /api/interact {op:'purchase', item}`
- `api/interact.js:223-291` → атомарний RPC (`purchase_premium` / `buy_likes_pass`
  / `purchase_swipe_pack`), який списує **тільки** якщо `stars_balance >= price`.

### Рейка Б — реальне поповнення (`op: 'create_stars_invoice'`)
Юзер платить реальні Stars через нативний лист Telegram; гаманець кредитується
**виключно** на вебхуці `successful_payment`.
- `paywall.js:242-284` → `POST /api/interact {op:'create_stars_invoice', packId}`
- `api/interact.js:303-325` → `createInvoiceLink` (currency `XTR`, `provider_token:''`,
  payload `deposit:<userId>:<packId>`) → клієнт `twa.openInvoice(...)`.
- Telegram → вебхук `POST /api/chat` (`update_id`) → `handleTelegramUpdate`
  (`analytics.js:139-148`) → `creditSuccessfulPayment` (`analytics.js:220-257`)
  → RPC `credit_stars_deposit` (ідемпотентний).

## 2. 🔴 P12-1 (P0 BLOCKER) — Вебхук платежів без підпису → безкоштовні Stars

### Пруф
`api/chat.js:31` — будь-який POST з полем `update_id` віддається у вебхук-гілку
**без жодної автентифікації транспорту**:
```js
if (body.update_id !== undefined) return handleTelegramUpdate(req, res, body);
```
`api/_lib/analytics.js:127-130` — гейт підпису **свідомо прибрано**:
```js
// ...the WEBHOOK_SECRET header gate was
// removed to eliminate setWebhook-secret sync as a failure mode. No update
// can trigger /stats without matching OWNER_TELEGRAM_ID.
```
`WEBHOOK_SECRET` визначено (`analytics.js:98`), але **ніде не звіряється** з хедером
`X-Telegram-Bot-Api-Secret-Token` (grep по всьому дереву: константа не читається жодного разу).

`analytics.js:145-146` — платіж обробляється **першим**, до будь-якої перевірки owner:
```js
if (msg && msg.successful_payment) { await creditSuccessfulPayment(msg); ... }
```
`analytics.js:222-243` — сума й отримувач беруться **прямо з тіла запиту**:
```js
const stars  = Number(sp.total_amount || 0);           // з тіла
const tgId   = msg.from && msg.from.id;                 // з тіла
const charge = sp.telegram_payment_charge_id;           // з тіла
const userId = parts[1] || null;   // з payload 'deposit:<userId>:<packId>' — з тіла
await supabase.rpc('credit_stars_deposit', { p_charge: charge, p_user: userId, p_tg: tgId, p_stars: stars, ... });
```

### Хиба в міркуванні автора
Коментар стверджує «isOwner захищає /stats, тож секрет не потрібен». Це правда **для
/stats**, але та сама неавтентифікована гілка обробляє **ПЛАТЕЖІ**, яких `isOwner`
**не захищає взагалі**. Підпис прибрали разом із захистом грошей.

### Репро (концептуально; НЕ виконував проти прода — RULE 1)
`userId` (uuid) клієнт бачить у відповіді `/api/me`; `tgId` — у власному initData.
Обидва — самообслуговувані. Зловмисник шле:
```
POST /api/chat
{ "update_id": 1,
  "message": { "from": {"id": <свій tgId>},
    "successful_payment": {
      "total_amount": 100000,
      "telegram_payment_charge_id": "forge-любий-унікальний",
      "invoice_payload": "deposit:<свій userId>:pack_250" } } }
```
→ `credit_stars_deposit` бачить свіжий `charge_id` → **+100000 ⭐ безкоштовно**.
Ідемпотентність **не рятує** — зловмисник просто щоразу міняє `charge_id`.
З 100k Stars безкоштовно купується Premium і всі платні фічі без обмежень.

### Money-impact
Максимальний. Уся Stars-економіка (Premium 150⭐, паси, репорт, реvia-фічі)
обходиться безкоштовно будь-ким, хто вміє слати POST. З рекламою — ллємо бюджет
на трафік, який монетизується у нуль.

### Фікс (~1–2 год)
1. `setWebhook(url=/api/chat, secret_token=<TELEGRAM_WEBHOOK_SECRET>)` (одноразово).
2. На початку вебхук-гілки (`api/chat.js:31` або першим рядком `handleTelegramUpdate`)
   звірити `req.headers['x-telegram-bot-api-secret-token'] === WEBHOOK_SECRET`;
   при розбіжності — `200 {ok:true}` без обробки (щоб не зливати наявність секрету).
   Env `TELEGRAM_WEBHOOK_SECRET` уже підключений — бракує лише порівняння + виклику setWebhook.
> **Синхронізація secret ↔ setWebhook — це керована операція розгортання, а не
> причина лишати гаманець відкритим.** Прибрати гейт заради «одного менш крихкого
> кроку деплою» — не той tradeoff.

## 3. Вебхуки — решта критеріїв ТЗ

| Критерій | Стан | Пруф |
|----------|------|------|
| Підпис | ❌ **НЕМАЄ** (P12-1) | `analytics.js:127-130`, `:98` |
| Ідемпотентність | ✅ по `charge_id` | `migration-018:42-49`, `migration-026:33-40` — `ON CONFLICT (charge_id) DO NOTHING`, кредит лише на свіжому insert |
| Порядок подій | ✅ `pre_checkout` → `successful_payment` | `analytics.js:139-148`; Telegram гарантує порядок |
| Повтори / at-least-once | ✅ безпечно | завжди `200` (`analytics.js:143,147,209`) + ідемпотентність = нема retry-шторму й дабл-кредиту |
| `pre_checkout` у 10 с | ✅ | `analytics.js:139-143` відповідає `ok:true` синхронно |
| Джерело істини | ✅ ledger `star_deposits` + `users.stars_balance` | `migration-018:17-24` |
| Розсинхрон платіжка↔БД | ⚠️ див. P12-2/P12-3 | немає звірки на «оплачено-в-Telegram-але-без-рядка» |

## 4. Успішна оплата → миттєвий доступ? Що бачить юзер?

- **Рейка А (трата):** доступ **миттєвий і атомарний**. Клієнт показує нотатку
  `pw_processing` (`paywall.js:301`), на успіху закриває лист і синхронізує кеш
  `sixtio_me` (`paywall.js:322-337`). Сервер повертає свіжий entitlement одразу
  (`interact.js:280-290`). ✅
- **Рейка Б (поповнення):** нарахування — на вебхуці (секунди). Клієнт **оптимістично**
  піднімає баланс на `openInvoice`-колбеку `paid` (`paywall.js:267-272`) і через
  2500 мс перечитує `/api/me` (`reconcileDeposit`, `:230-240`). Фічі, що витрачають
  Stars, доступні щойно кредит ліг. ✅ (race — P12-5, косметичний).

## 5. Погані сценарії checkout

| Сценарій | Поведінка | Пруф |
|----------|-----------|------|
| Відхилення / `failed` | Нотатка `pw_pay_fail`, гаманець не чіпається | `paywall.js:273-274` |
| Закриття вікна / back / `cancelled`/`pending` | No-op, нотатка очищена | `paywall.js:275-277` |
| Картка / 3DS | **N/A** — Stars = внутрішній гаманець Telegram, карток немає | `provider_token:''` `interact.js:316` |
| Подвійний тап | Клієнт: guard `busy` (`paywall.js:210,252,300`). Сервер: атомарний RPC `WHERE stars_balance >= price` — оверспенд неможливий незалежно від клієнта | `interact.js:238-257`, `migration-010:70-82` |
| Дві вкладки / два інстанси | Те саме: кожне списання атомарне й guarded; двічі купити Premium = двічі списати й **стекнути** час (`greatest(now, premium_until)+days`), юзер отримує оплачене, не втрату | `migration-010:77` |
| Дубль реального платежу | Кожен реальний платіж = унікальний `charge_id` → 2 платежі = 2 кредити (коректно) | `migration-018:42-49` |

## 6. Скасування / refund / chargeback / dunning / grace

- **Підписки немає** → dunning / продовження / прорація / grace-період **N/A за дизайном**
  (Premium — разові 30 днів, лапсається на `premium_until` без grace; для one-off це очікувано).
- **Chargeback** — N/A (Stars, не картки).
- **Refund — P12-2 (P2):** обробки рефанду **немає ніде** (grep `refund`: лише коментарі
  `interact.js:715`, `migration-035:63`, які пояснюють свідому відмову будувати рефанд).
  Якщо власник/Telegram повертають Stars за депозит — **гаманець не дебетується**,
  `star_deposits`/`stars_balance` розсинхронізуються з реальними грошима.
  Експлуатованість обмежена (рефанд ініціюється власником/через підтримку Telegram,
  не self-serve юзером), тому P2, а не P1. Фікс: обробити refund-сигнал і дебетувати
  гаманець (clawback), або регулярна ручна звірка ledger.

## 7. Restore purchases / новий пристрій

✅ **Сильна сторона.** Restore-флоу **не потрібен**: entitlement серверний і прив'язаний
до Telegram id (`premium_until`, `stars_balance` у рядку `users`). Будь-який пристрій,
що автентифікує той самий Telegram-акаунт, бачить той самий баланс і Premium.
Крос-девайс — безкоштовно й автоматично. `entitlements.js:25-50`.

## 8. Тарифи / прорація / промокоди

- Тарифів немає — один SKU Premium, апгрейд/даунгрейд/прорація **N/A**.
- **P12-4 (P3):** лутбокс має виграш `discount_30` (`interact.js:42`), i18n показує
  «−30% на Premium» (`i18n.js:78/445/794`), **але `purchase('premium')` бере фіксований
  `PREMIUM_PRICE=150` без жодного параметра знижки чи збереженого стану знижки**
  (`interact.js:238-243`, `migration-010:70`). Grep `discount` не знайшов ні колонки,
  ні шляху редімпшену → виграна знижка **ніде не застосовується**. Обіцянка без
  реалізації = удар по довірі. НЕ ЗМІГ ПЕРЕВІРИТИ на 100% (треба глянути, чи лутбокс
  десь не пише discount-флаг), але шлях checkout входу для знижки не має — сигнал сильний.

## 9. Валюти / ціни по країнах / податки

- Єдина валюта — **XTR (Stars)**; застосунок показує фіксовані суми зірок скрізь однаково.
- Фіатну конвертацію, регіональні ціни Stars і податки/ПДВ повністю тримає **Telegram
  (та Apple/Google на своєму боці)** — застосунок **ніколи не торкається фіату**.
- Для Stars-only це **коректно**: локалізація ціни й VAT-облік у застосунку не потрібні.
  Ризик низький.

## 10. Тестовий режим у проді / ключі

- `provider_token: ''` (`interact.js:316`) — **правильно** для Stars; провайдерського
  test/live-ключа, який можна лишити або злити, **не існує в цьому шляху**. Немає Stripe/тест-ключів.
- `STAR_PACKS` (`interact.js:27-31`) — реальні пакети 50/100/250, тестових SKU
  (`pack_1`/`test`) немає.
- Єдиний тест-тумблер — `ALLOW_FAKE_AUTH` (не платіжний ключ); CLAUDE.md забороняє його
  на Vercel. Має бути OFF у проді (перевірено в попередніх фазах).

## 11. Сильні сторони (зафіксувати, щоб не «зламати фіксом»)

- Ідемпотентність по `charge_id` — дабл-кредит для справжніх вебхуків неможливий.
- Списання — атомарні guarded-RPC (`purchase_premium`/`buy_likes_pass`/`purchase_swipe_pack`/
  `purchase_ai_report`): оверспенд і race-дабл-спенд неможливі.
- Ціна й entitlement — авторитет сервера; клієнтська ціна суто для відображення
  (`paywall.js:293-294`, `interact.js` ігнорує клієнтську ціну).
- AI-репорт: «charge-first, потім генерація» з ідемпотентним `purchase_ai_report` і
  безкоштовною регенерацією при збої (`interact.js:712-724`) — не буде «заплатив за ніщо».
- Завжди `200` вебхуку — немає retry-штормів.
- Крос-девайс/restore — безкоштовно (серверний entitlement).

## 12. НЕ ЗМІГ ПЕРЕВІРИТИ

1. **P12-4 редімпшен знижки** — чи не зберігає лутбокс десь discount-флаг, який читає
   інший шлях купівлі. Як перевірити: grep колонок `discount%` у міграціях + прочитати
   RPC `open_lootbox` (migration-013) на предмет запису стану знижки.
2. **Реальний вебхук на живому боті** — підтвердити, що прод-бот справді має `secret_token`
   (або не має) можна лише через `getWebhookInfo` бот-API (потребує токена; RULE 1 — не
   чіпав прод). Але з коду однозначно: навіть якщо secret на боці Telegram виставлений,
   сервер його **не звіряє**, тож захисту немає.

## Пріоритети до реклами

- **P12-1 (P0) — блокер запуску реклами.** Без нього кожен, хто відкрив DevTools,
  отримує безкоштовну економіку; платний трафік монетизується в нуль. Фікс ~1–2 год.
- **P12-2 / P12-3 (P2)** — зробити після P0: refund-clawback + reconcile втраченого top-up.
- **P12-4 / P12-5 (P3)** — прибрати недосяжний виграш знижки (або реалізувати редімпшен);
  косметика reconcile.

> Нагадування (RULE 1): жодних правок не вношу до явного «фіксимо». P12-1 — очевидний
> перший кандидат.
