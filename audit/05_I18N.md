# ФАЗА 5 — Мови (uk / en / ru)

**Режим:** READ-ONLY. Жодних правок коду. Пруфи: `файл:рядок` + цитата / реальний вивід.
**Ринки:** uk (дефолт) · ru · en. Німецька/польська **не** в скоупі — тому пункт «переповнення тексту» має низький пріоритет (uk↔ru приблизно однакової довжини, en зазвичай коротший).

## 0. TL;DR

Локалізація тут **зріла і, місцями, зроблена краще, ніж у 90% продуктів**: автоматичний чекер чистий, плюралізація uk/ru реалізована **правильно** (3 форми, не наївне one/many), а бот-пуші повністю локалізовані під мову **отримувача**. Це рідкість.

Але є **одна архітектурна діра, що прямо б'є по платному трафіку** (I18N-1): вбудований перемикач мови UA/RU/EN **ніколи не надсилається на сервер**. Тому він перемикає лише статичний клієнтський текст, а весь **серверний/AI-контент** (біо, причини метчу, Digital Twin, AI-звіт) і **всі бот-пуші** лишаються мовою **Telegram-акаунта**. Саме сценарій, заради якого перемикач і робили (Telegram Desktop), — зламаний.

## 1. Покриття ключів: матриця locale × key

`npm run i18n` (scripts/i18n-check.mjs) — реальний вивід:

```
i18n-check — 481 keys (uk 481 · en 481 · ru 481)

Clean.
```

- **Відсутніх ключів (MISSING): 0.** Кожен із 481 ключів визначено у всіх трьох мовах.
- **Невизначених (UNDEFINED — код просить, словник не має): 0.**
- **Hardcoded Cyrillic поза словником: 0** (у скоупі чекера — кореневі `*.html`/`*.js`).

> Обмеження чекера, які я закрив вручну нижче: він не бачить (а) `api/**` — там живуть бот-пуші; (б) плюралізацію; (в) формати дат/чисел; (г) латиницю, вписану в код (ловить лише кирилицю); (д) **ключі-сироти** (визначені, але ніде не використані) — чекер шукає лише зворотне.

### Ключі-сироти (orphans) — визначені, ніде не викликаються

Власний скан (`scratchpad/orphan.mjs`): з 481 ключа після відсіву **рантайм-родин** (`kink_*`, `interest_*`, `value_*`, `sign_*`, `soc_*`, `elem_*`, `report_sec_*` — будуються як `t(prefix + code)`, напр. `profile.html:1354 t('soc_'+code)`, `:1463 t('elem_'+…)`, `:1498 t('report_sec_'+s.key)`) лишаються **справжні сироти**:

```
achieve_empty · achieve_next · aria_edit · dark_hint · dark_off ·
depth_q_default · improve_btn · likers_open · match_locked_hint ·
mn_cancel · mn_report_ph · mn_unblock · mn_unblocked ·
pw_locked_subtitle · report_axes_l
```

≈15 ключів × 3 мови ≈ **45 мертвих рядків**. Самі по собі не баг, але:
- `mn_unblock`/`mn_unblocked`/`mn_report_ph`/`mn_cancel` — схоже на **недороблене меню блокування/скарги**. Ядро модерації **таки підключене** (`api/interact.js:106` `op==='block'||'unblock'`, `:107` `op==='report'`, `:771` `blockUser`), а UI-варіанти *unblock* і *плейсхолдер причини скарги* — мертві. Тобто заблокувати можна, а **розблокувати з UI — ймовірно ні**; поле причини скарги, схоже, без локалізованого плейсхолдера. Для платного трафіку модерація критична — див. рекомендацію в §2.

**Оцінка:** P3. Прибрати мертві ключі АБО дописати unblock/report-reason UI (рішення продукту).

## 2. Хардкоджені рядки (тости / alert / помилки / пуші / платіжні екрани)

- **Кирилиця поза словником у клієнті:** 0 (i18n-check Clean).
- **Латиниця, вписана як user-facing текст:** не знайдено значущих випадків у клієнті — платіжні написи йдуть через `t('pw_*')`, `paywall.js:160 t('pw_likes_note', …)`.
- **Серверні JSON-помилки** (`{error:'Internal error'}` тощо) — англійські, але **не рендеряться** користувачу (доведено у Фазі 6): клієнт кидає узагальнений `HTTP nnn` і показує локалізоване копі.
- **Бот-пуші (Telegram-повідомлення поза Mini App)** — **повністю локалізовані**, див. §9. Єдині хардкод-рядки в бот-шарі — **адмінські**, не для користувача: `api/_lib/commands.js:338 '✅ Відповідь надіслано.'`, `:342 '⚠️ Не вдалося надіслати: …'` — відповідь власника на фідбек, отримувач = OWNER. Прийнятно.

**Рекомендація (ad-safety):** оскільки block/report вже є на сервері — переконатись, що кнопки «Поскаржитись»/«Заблокувати» реально доступні з екрана діалогу перед стартом реклами (Meta/Google цінують видиму модерацію в dating-застосунках). Це не баг копірайту, а гейт готовності — винесено як завдання для Фази 38 (in-browser).

## 3. Плюралізація і відмінки — **зроблено правильно**

`i18n.js:1261-1272`:

```js
function plural(base, n) {
  var key;
  if (lang === 'uk' || lang === 'ru') {
    var last = n % 10, teen = n % 100;
    if (last === 1 && teen !== 11) key = '_one';
    else if (last >= 2 && last <= 4 && (teen < 12 || teen > 14)) key = '_few';
    else key = '_many';
  } else {
    key = n === 1 ? '_one' : '_many';
  }
  return t(base + key, { n: n });
}
```

Це **коректне** правило слов'янської множини за останньою цифрою з винятком підліткових 11–14 (1 людина / 2 людини / 5 людей / **21** людина / **11** людей). НЕ наївне `count===1?a:b`. Пруф трьох форм у словнику: `likers_sub_one/few/many` (`i18n.js:150-152` uk, `:511-513` en, `:860-862` ru).

**Конкатенації рядків із числом** («Ви маєте » + n + « днів») у словнику **немає** — усе через плейсхолдери `{n}`/`{d}`/`{x}`/`{total}` з підстановкою в `t()` (`i18n.js:1243-1249`).

### I18N-3 (P3) — два місця повз `plural()`

`i18n.js:156` `likers_pass_btn: 'Показати всіх на {d} днів · {p} ⭐'` та `:371` `pw_likes_note: '…{d} днів…'` вставляють число поруч із **фіксованим** «днів»/«дней». Граматично вірно **лише тому, що `d` завжди 7** (`paywall.js:9 LIKES_PASS_DAYS = 7`; `matches.html:454 t('likers_pass_btn', { d: data.passDays … })`). Якщо конфіг колись стане 1 / 2 / 22 — вийде «1 днів», «22 днів». Латентний баг.
Контраст — **правильний** патерн поруч: `likers_pass_on: 'Усі відкриті ще {d} дн.'` (`:157`) використовує інваріантне скорочення «дн.», яке не схиляється. **Оцінка:** P3, латентно. Фікс: або через `plural('likers_pass_days', d)`, або перевести на скорочення «дн.».

## 4. Формати (дати, час, числа, валюта)

- **Валюта** — лише Telegram Stars (`⭐`/XTR), позиція стабільна: «40 ⭐», «{p} ⭐». Консистентно на всіх екранах.
- **Відносний час** у чат-листі локалізований через словник: `time_now/time_min/time_hour/time_yesterday` (`i18n.js:147` uk / `:508` en / `:857` ru), рендер `chat.html:111-120 relTime()`.
- **I18N-4 (P3):** `chat.html:119 return d.toLocaleDateString();` — для дат, старших за 2 дні, формат береться з **локалі пристрою**, а не з мови застосунку. Користувач, що перемкнув UI на ru на пристрої з en-локаллю, побачить дату у форматі M/D/Y. Дрібна неконсистентність. Фікс: `d.toLocaleDateString(SixtioI18n.lang)`.
- Часові пояси / перший день тижня / формат телефону / адреси — **не застосовні**: продукт не показує календарів, не збирає телефон і адресу (лише місто вільним текстом через геокодер). Немає чого локалізувати.

## 6. Якість перекладу / ти-ви / терміни

- **Змішування «ти/ви»** — підтверджено ще у Фазі 6 (COPY-5, P3): перший екран на «ви» (`idx_note` «Вашого профілю…»), решта продукту на «ти» (`idx_sub`, кнопки). Дублікат — не заводжу окремо, лишаю в COPY-5.
- **Різнобій термінів** «метч / збіг / пара» — теж COPY-5.
- **Машинний присмак / кальки:** точкові, не системні. ru-блок написаний природно (`feed_kicker: 'Твоя подборка на сегодня'`, `wf_free_note`), en-блок ідіоматичний (`likers_sub_one: '{n} person is waiting for your answer'`). Окремих P0/P1 з якості перекладу немає.

## 7. Дефолтна мова, перемикач, персистентність — **головна знахідка**

### Що працює
- **Детекція** (`i18n.js:1100-1230`): мова тягнеться СТРОГО з живого Telegram SDK (`initDataUnsafe.user.language_code`, з фолбеком на розпарсений `initData`), з відновленням `en` з порожнього коду через `navigator.language`. Клієнт і сервер (`telegram.js:54 resolveLang`) мапляться в lock-step: `uk→uk`, `ru/be→ru`, інше→`en`, порожнє→`uk`.
- **Персистентність вибору** локально: `setLang` пише `sixtio_lang_override` в localStorage, **namespaced на акаунт** через `lsKey()` (`i18n.js:1358`), і `detect()` віддає перевагу override назавжди. **Переживає reload і повернення з оплати**: після успіху Stars `paywall`/сторінка робить `location.reload()`, а на перезавантаженні `detect()` читає override → мова відновлюється. OAuth у продукті немає.

### I18N-1 (P2 → P1 для Desktop-трафіку) — вибір мови не доходить до сервера

**Задум** (коментар `telegram.js:64-72`): клієнт шле `lang` на КОЖНОМУ виклику, і сервер бере його через `pickLang(clientLang, tgUser)` замість мови акаунта — «*so AI content and stored bot-notification language must follow the switcher instead*». `me.js:124` пише `language_code: pickLang(body.lang, tgUser)`, `me.js:208` рендерить контент цією ж мовою.

**Реальність:** `body.lang` **не надсилається ніде**. Пруф — grep по всіх сторінках на `lang:` у тілах запитів: **порожньо**. Обгортки `api()` шлють лише `Object.assign({ initData }, payload)` (`chat.html:126`, `matches.html:242`, `profile.html:605`, `feed.html:366`, `onboarding.html:230`, `conversation.html:158`), `/api/me` викликається з `{}` (`chat.html:213`, `matches.html:531`, `profile.html:895`, `onboarding.html:783,813`) або лише з `initData` (`index.html:113`). Єдине використання `SixtioI18n.lang` у запиті — геокодер Nominatim (`onboarding.html:463 accept-language=`), до нашого сервера стосунку не має.

**Наслідок** (`pickLang` при `clientLang=undefined` → `resolveLang(tgUser)` = мова акаунта, `telegram.js:76`):
1. **Серверний/AI-контент** (біо `bio_i18n`/`translate.js`, причини метчу, Digital Twin, AI-звіт) завжди мовою **Telegram-акаунта**, не перемикача. Користувач перемикає UI ru→en → статичні написи стають en, а **біо і причини метчу лишаються ru**. `setLang` навіть скидає кеш `sixtio_me` (`i18n.js:1374`) в надії, що «*сервер поверне текст перекладеним*» — але серверу нову мову ніхто не сказав, тож він повертає стару. Частковий, збиваючий з пантелику перемик.
2. **Усі бот-пуші** (метч, нове повідомлення, instant-match, retention, реферальний бонус) йдуть за `users.language_code`, який виставляється лише з мови акаунта → **перемикач їх не чіпає**.
3. Ламається **саме той сценарій**, заради якого перемикач і зробили: на Telegram Desktop `language_code` = мова акаунта ≠ обрана мова інтерфейсу (це прямо написано в коментарі `pickLang`).

**Money-impact:** платний трафік часто заходить із Desktop і з не-цільовою мовою акаунта. Людина обирає свою мову в UI, але отримує біо/причини метчу і **пуш «у вас метч» чужою мовою** → падіння активації і повернень саме на трафіку, за який заплачено. Тому для реклами піднімаю ефективний пріоритет до P1.

**Фікс (орієнтовно 1–2 год):** додати `lang: SixtioI18n.lang` в тіло КОЖНОГО запиту (найчистіше — один раз в обгортки `api()` на всіх сторінках + явні `fetch('/api/me')` в `index.html`/`match.html`). Сервер уже готовий це прийняти (`pickLang`). Спільний ассет НЕ чіпається окремо, але після зміни — bump `?v=` на всіх сторінках, `npm test`, `npm run i18n`, перевірка в браузері. *Код не чіпаю до команди «фіксимо».*

## 8. Мова стору / лендінга / креативів = мова продукту

**I18N-5 — НЕ ЗМІГ ПЕРЕВІРИТИ:** немає матеріалів — ні тексту бот-стартового екрана `/start` для звірки, ні лістингу в каталозі Telegram/сторі, ні рекламних креативів. Це та сама залежність, що COPY-2 з Фази 6.

Ризик, який треба закрити перед відкриттям трафіку: якщо оголошення російською веде на бот, чий `/start` і перше повідомлення — українською (бо `resolveLang` мапить порожній код у `uk`), користувач із реклами падає в «чужу» мову ще до Mini App і відвалюється. Стартове бот-копі локалізоване (`commands.js` uk/en/ru), але **вхідна мова визначається мовою акаунта, не мовою оголошення** — тож креатив і мова акаунта цільової аудиторії мають збігатися.

`Як перевірити вручну: дай (1) текст /start бота, (2) лістинг у Telegram-каталозі/сторі, (3) креативи по мовах — звірю дослівно проти мови продукту і проти I18N-1.`
