## 1. ВЕРДИКТ

# 🔴 NO-GO — сьогодні рекламу вмикати не можна.

Після закриття 5 безумовних P0 (≈6 робочих днів) вердикт стає **GO WITH FIXES**.

**Обґрунтування (3 речення).**
Платіжний вебхук `/api/chat` не перевіряє жодного підпису, тому будь-хто може
надіслати підроблений `successful_payment` і намайнити собі необмежену кількість
Stars — уся монетизація, заради якої купується трафік, знецінюється в перший же
день (`12_PAYMENTS.md` §2, `analytics.js:98,128`). Одночасно застосунок не витримує
саме того обсягу, на який націлена реклама: `calculate_compatibility` повертає весь
scored-набір профілів без `LIMIT` на кожен відкрив застосунку — навантаження росте
як O(N²) і при 10 000 профілів дає 39 ГБ/добу egress (`10_SCALE.md` §1). І якщо це
зламається о 23:00 у суботу, ніхто не дізнається: моніторингу помилок і аптайму
немає взагалі, а єдина публічна проба `/api/geo` віддає 200, не торкаючись ні БД,
ні AI, ні Telegram (`14_INCIDENTS.md` §1–2).

**Що НЕ є причиною NO-GO — і це варто сказати прямо.** Продукт не сирий. Копірайт
зрілий і тримовний (i18n-check Clean, 481 ключ ×3), мертвих кнопок і заглушок не
знайдено жодної (`04_BUTTONS.md` §0), списання Stars — атомарні guarded-RPC,
нарахування ідемпотентне по `telegram_payment_charge_id`, воронкові події
деривуються на сервері з дії, а не з клієнта. Блокери — інфраструктурні й
юридичні, а не продуктові; вони фіксяться за тиждень, а не за квартал.

## 2. ТОП-10 ризиків для рекламного бюджету

Відсортовано за **очікуваною втратою**. Втрати оцінені на прогнозі Фази 10
(10 000 кліків/добу → 4 000 стартів → 1 000 онбордингів) і на **явному
припущенні** CPC $0.15–0.30, тобто денний бюджет $1 500–3 000. Якщо ваш бюджет
інший — множник змінюється, порядок ризиків ні.

### 🟡 SEC-3 (P1, ВІДКЛАДЕНО ДО ВИМІРЮВАННЯ) — signed URLs можуть роздути egress

**Наслідок SEC-1.** Після переходу бакета `photos` у private (міграція 040) кожне
фото віддається через `createSignedUrl`. На тарифі Supabase **Free** CDN бере
`?token=` у ключ кешу, і кожен унікальний токен = окремий запис → перший запит за
будь-яким signed URL завжди cache MISS (тягне з origin). Supabase вшиває у токен
`iat` (момент видачі), тож два виклики того самого файлу навіть за секунди дають
**різні** рядки (доведено емпірично 2026-07-31: `exp` однаковий, `iat` різний,
`TOKENS IDENTICAL: false`). Самотужки згенерувати детермінований токен не можна —
signed URL підписуються окремим внутрішнім ключем storage, недоступним застосунку
(підтверджено доками Supabase). Тому підписані URL можуть з'їдати **більше** egress,
ніж публічний бакет (де HIT-рейт високий), і на Free це прямий ризик перевищення ліміту.

**Поведінка «CDN ігнорує токен у ключі кешу» (Smart CDN) доступна лише від Supabase Pro** —
власник купує цього тижня. Тому фікс тримаємо відкладеним, а не робимо зараз (передчасна
оптимізація при 6 користувачах).

**Умова спрацювання:** після переходу на Pro і появи перших реальних користувачів
звірити графік egress Storage. Якщо фото їдять непропорційно — повернутись до
**мемоізації спільного рядка** (нижче). **Перевірити ОБОВ'ЯЗКОВО до запуску реклами.**

**Готовий робочий варіант (щоб не досліджувати вдруге)** — мемоізувати сам рядок
signed URL на (ключ, 10-хв вікно), щоб усі глядачі вікна отримували байт-у-байт
однаковий URL (CDN/браузер HIT у межах одного екземпляра лямбди; для HIT між
екземплярами — зберігати рядок+вікно у БД). У `api/_lib/photos.js`:

```js
const CACHE_WINDOW_SEC = 600;            // 10-хв спільне вікно
const urlCache = new Map();              // key -> { url, windowStart }  (≤ 1 на юзера)
function windowedSign() {
  const now = Math.floor(Date.now() / 1000);
  const windowStart = Math.floor(now / CACHE_WINDOW_SEC) * CACHE_WINDOW_SEC;
  const exp = (Math.floor(now / CACHE_WINDOW_SEC) + 2) * CACHE_WINDOW_SEC; // TTL 1×–2× вікна
  return { windowStart, expiresIn: exp - now };
}
// signPhoto: якщо urlCache.get(key).windowStart === windowStart → віддати кешований рядок;
// інакше createSignedUrl(key, expiresIn), покласти в кеш, віддати. signPhotos: те саме батчем.
// Безпека не змінюється: URL прив'язаний до ОБ'ЄКТА, blur/entitlement вирішено ДО виклику.
```
Обмеження: різні екземпляри лямбди в одному вікні дадуть різні рядки (різний `iat`) →
до N варіантів на вікно, N = число теплих екземплярів. На Free з малим трафіком N≈1–2.
Заразом за потреби виставити `cacheControl` при upload у `api/photo.js` (зараз відсутній →
дефолт 3600с); понад довжину вікна сенсу мало, бо URL ротуються щовікна.

| # | Інцидент | Тривалість | Чому було не видно |
|---|---|---|---|
| 1 | `Invalid supabaseUrl` — значення `SUPABASE_URL` у Vercel зіпсоване при ротації; `createClient` кидав на кожному запиті з даними | **~13.5 год** (2026-07-31 17:36 → 08-01 07:11) | 500 лише на автентифікованих запитах; перевірка «чи живий прод» пінгом без initData давала 401 і виглядала чистою |
| 2 | `translateBundle failed: Gemini 404` — модель недоступна | **~7 діб** (з 2026-07-25 11:41, триває) | `translate.js:67` ловить помилку і повертає `{}`; ендпоінт віддає **200**, користувач бачить неперекладений текст |
| 3 | `cron_retention_trigger failed` — ретеншн-пуші не йшли нікому | **~12.5 год** (2026-07-31 17:00 → 08-01 05:30) | наслідок #1; крон нікому не звітує, «нуль надісланих» і «крон мертвий» ззовні не відрізнити |

Спільна форма всіх трьох: **конфігураційне значення неправильне → нічого не
падає достатньо голосно → єдиний слід це лог, якого ніхто не читає.** Два з
трьох повертали HTTP 200.

**Закрито частково (2026-08-01):**
- `api/_lib/env.js` — `validateEnv()`: перевірка *форми* всіх 14 змінних плюс
  загальні хвороби (пробіли по краях, лапки, перенос рядка, літерал
  `[SENSITIVE]`). `OWNER_TELEGRAM_ID` перевіряється **першим і окремим рівнем**:
  це сам канал сигналізації, без нього `notifyOwner` — тихий no-op, і жоден
  інший алерт нікуди не дійде. 27 тестів (`test/env.test.js`).
- `reportEnvOnce()` на module-load у `_lib/supabase.js` (спільна точка всіх 11
  функцій, що ходять у БД). Свідомо **не кидає**: падіння на імпорті
  перетворило б опечатку в `APP_URL` на повну аварію — гірше за проблему, яку
  воно лікує.
- `smokeEnv()` — по одному живому виклику на залежність (Supabase `count`,
  Telegram `getMe`, Gemini `models.list` зі звіркою моделі, що реально
  використовується, Anthropic `models`). Викликається з ретеншн-крона
  (`api/me.js`) — вже запланований, вже авторизований, **поза шляхом запиту**;
  провал → `notifyOwner`. Цей димовий тест зловив би #1, #2 і #3.
- `/envcheck` — та сама перевірка на вимогу, лише для власника, відповідь
  списком ✅/❌ **без значень**. Живе в `_lib/commands.js` → нуль нових функцій.

**Лишається відкритим:** зовнішній аптайм-пінг (`/api/health` як і раніше 404) і
збереження логів — на Hobby вони не переживають ніч, тож ретроспективний розбір
довших за годину інцидентів досі неможливий.

### 🔴 AI-1 (P0, ВІДКРИТО) — Gemini 404: уся AI-периферія може бути мертвою

`GEMINI_MODEL` **не виставлений у Vercel узагалі** (перевірено `vercel env ls`:
у Production/Preview є лише 9 змінних, цієї серед них немає). Тому всі п'ять
місць виклику беруть хардкод-дефолт `gemini-2.5-flash`
(`gemini.js:5`, `gemini.js:55`, `translate.js:38`, `personality.js:96`,
`kink.js:56`), і саме на ньому `generativelanguage.googleapis.com/v1beta`
віддає **404**.

Отже це **не опечатка в змінній** — значення ніхто не міняв. Помилка виникла
сама, 2026-07-25, без жодного коміту й без зміни конфігурації. Це підпис
серверної події на боці Google (виведення моделі з експлуатації), а не нашої
регресії.

**Радіус ураження ширший за переклад.** У логах видно лише `translateBundle`,
бо він викликається на кожному `/api/me` для читача з іншою мовою. Решта
Gemini-функцій рідкісні (онбординг, покупка звіту), тому просто ще не
потрапили у вікно логів — але всі вони йдуть через той самий рядок:

| функція | точка виклику | поведінка при 404 |
|---|---|---|
| **модерація фото NSFW** | `api/photo.js:53` → `moderatePhoto` | **fail-open** (`photo.js:58-60`) — фото приймається без перевірки. Для 18+ застосунку це прямий ризик, і ручні перевірки фото цього не показують: вони й мають проходити |
| Big Five / Digital Twin | `analyze-traits.js` → `processOnboardingPersonality` | кидає → онбординг не завершується |
| kink-маркери (18+) | `interact.js` → `processKinkInterview` | кидає |
| AI-звіт (**платний, 50 ⭐**) | `interact.js` → `generateAiReport` | кидає — користувач платить і не отримує |
| follow-up питання | `answer.js` → `generateFollowup` | деградація інтерв'ю |
| «чому ви підходите» | `chat.js` → `generateWhyFactor` | деградація |

**Що зробити:** отримати список доступних моделей і виставити `GEMINI_MODEL`
у Vercel. Перевірити не з локальної машини не вийшло — `GEMINI_API_KEY`
позначений Sensitive і в `env pull` приходить як `[SENSITIVE]`; потрібен ключ
із AI Studio. Після виправлення варто оновити й хардкод-дефолт у п'яти місцях,
бо зникла змінна знову впаде на мертву назву. Найкраще — плаваючий аліас
(`*-latest`), щоб наступне виведення моделі не повторило цей інцидент.

Оновлений `smokeEnv()` тепер звіряє модель зі списком і називає проблему явно —
цей самий баг більше не проживе тиждень непоміченим.
