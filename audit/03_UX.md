# ФАЗА 3 — UI/UX під холодний рекламний трафік

**Роль:** песимістичний head-of-eng + QA + growth. Читав кожну сторінку та `theme.css`,
`paywall.js`. Все READ-ONLY. Кожна теза — з `file:line` + цитатою.

Трафік заходить `index.html → onboarding.html`, далі таб-бар `feed/matches/chat/profile`.
Це і є критичний шлях; його й міряю найсуворіше.

---

## 0. TL;DR

Візуально застосунок дуже вилизаний і місцями зразковий (reduced-motion / reduced-transparency /
prefers-contrast у `theme.css:207-216`, оптимістичне фото з revert на NSFW, атомарні guard-и проти
дабл-сабміту в фіді/пейволі, повний набір empty-станів). Але для **холодного** трафіку є кілька
дір, які коштують конверсії у воронці, і купа таргетів <44px.

**Головне під рекламу:**
- 🟠 **UX-1 (P1):** `onboarding.html` — **порожній перший екран**, поки не відповість `/api/me`
  (до 25 c таймаут). Це буквально перший екран воронки після кліку з реклами.
- 🟠 **UX-2 (P2):** `matches.html` і `chat.html` не мають ані loading-, ані error/offline-стану без
  кешу — при збої мережі юзер бачить майже порожній екран без спінера й без «повторити».
- 🟡 **UX-3 (P2):** десятки тап-таргетів <44×44 (усі «✕» = 34×34, шестерні/бек = 40×40).
- 🟡 **UX-7 (P2, trust):** тумблери в `settings.html` — **бутафорія** (localStorage або статичний
  текст), нічого не роблять на сервері. «Показувати мене / інкогніто» вимикаються «в нікуди».
- 🟡 **UX-5 (P3, баг):** `match.html` навішує обробники всередині `render()`, який зветься двічі
  (кеш + свіжий `/api/me`) → кнопки «Чому ми підходимо» та «Написати» отримують **по 2
  слухачі**; тап відкриває дві overlay / подвійну навігацію.

Далі — деталізація.

## 1. Перше враження (5 секунд, один CTA)

**Добре.**
- `index.html` малює статичний герой миттєво (жодних API-залежностей для першого кадру), теза
  зрозуміла, **один** головний CTA: `index.html:77` `«Познайомитись із Sixtio»`. Персональне
  привітання по імені з Telegram (`index.html:90-99`) — сильний хід.
- Повернений юзер із профілем одразу редіректиться на `matches.html` (`index.html:123`), не
  застрягає на лендингу.

**Проблема — наступний екран.**

### 🟠 UX-1 (P1) — onboarding.html стартує з порожнього екрана

**Пруф:** `onboarding.html:811-830` — гілка init для нового юзера:
```js
api('/api/me', {}).then(function(me){ ... askNextProfile(); })
```
`askNextProfile()` (перше повідомлення бота + прогрес) викликається **тільки після** резолву
`/api/me`. До того `#chat` порожній, `progress-fill` = 0%, `stepLabel` = `&nbsp;`. Таймаут запиту —
`onboarding.html:232` `setTimeout(abort, 25000)`. Тобто на повільному 3G/поганому конекті **перший
екран воронки — біла порожнеча до 25 секунд**, без спінера, без typing-індикатора.

Іронія: у застосунку вже є готовий `startTyping()` (`onboarding.html:283-291`) — його просто не
показують під час стартового запиту.

**Money-impact:** це №1 екран після кліку з платної реклами. Порожній перший кадр = миттєвий
відвал частини CPC-трафіку ще до першого питання. Прямо б'є по CR onboarding-start.
**Фікс (~30 хв):** показати `startTyping()` / скелет першого бабла одразу при завантаженні, до
відповіді `/api/me`; прибрати indicator у `askNextProfile()`.

## 2. Стани асинхронних блоків (loading / empty / error / offline / success / partial)

Зведення по сторінках:

| Сторінка | loading | empty | error/offline (без кешу) | success |
|---|---|---|---|---|
| index | n/a (статик) | — | тихо лишається лендинг ✅ | редірект ✅ |
| onboarding | ❌ (UX-1) | n/a | ✅ fallback на askNext (`:823`) | ✅ картка |
| feed | ✅ спінер (`:270`) | ✅ `💜 feed_empty` | ✅ `📡 feed_net_error` (`:756`) | ✅ |
| matches | ❌ немає | ✅ banner/emptyHint | ❌ **порожньо** (`:555`) | ✅ |
| chat | ❌ немає | ✅ `chat_empty` | ❌ **порожньо** (`:217`) | ✅ |
| conversation | ❌ (одразу poll) | ✅ intro | ⚠️ тихо тримає стан (`:263`) | ✅ |
| profile | cache-first | ✅ nudge-и | ⚠️ порожній кістяк | ✅ |
| match | cache-first | редірект | ⚠️ тихо (`:349`) | ✅ |

**`feed.html` — еталон:** спінер + окремі empty/error-стани. Решту треба підтягнути до нього.

### 🟠 UX-2 (P2) — matches.html і chat.html: немає loading та error без кешу

**Пруф matches:** `matches.html:555` `load().catch(function(){ /* offline — cache already shown */ });`
Якщо кешу `sixtio_me` немає (нова сесія/очищений сторедж) і мережа впала — `render()` не викликається
жодного разу. На екрані лишаються тільки заголовок і кнопка «Знайти пару»; `searchBanner`, `emptyHint`,
`likesCard`, `premiumTeaser` усі `hidden` за замовчуванням. Ані спінера, ані «Повторити».

**Пруф chat:** `chat.html:213-217` — той самий патерн, при збої без кешу лишається порожній `#list`
(і `empty` теж `hidden`, бо його розкриває лише `render()`).

**Фікс (~1 год на обидві):** початковий спінер + catch-гілка з error-станом і кнопкою «Повторити»
(скопіювати підхід із `feed.html:753-760`).

### ⚠️ Partial/optimistic — де стани змішуються тихо
- `conversation.html:329-331` — при фейлі надсилання текст **тихо** повертається в інпут, без будь-якого
  сигналу помилки. Юзер не знає, що не відправилось (див. UX-9).
- `profile.html` cache-first: до відповіді `/api/me` картка показує **порожні** секції (ім'я порожнє,
  bio-nudge), потім наповнюється. Без кешу й офлайн — лишається порожній кістяк без явного стану.

## 3. Тапабельність — цілі < 44×44

Систематично дрібні керуючі елементи. Список із пруфами (усе у px, дизайн-одиниці):

| Елемент | Розмір | Пруф |
|---|---|---|
| «✕» закриття лайкерів | 34×34 | `matches.html:128` `.lk-close` |
| «✕» Why-overlay | 34×34 | `match.html:104` `.why-close` |
| «✕» AI-звіт / edit sheet | 34×34 | `profile.html:193` `.rp-close` |
| «✕» consent/interview | 34×34 | `profile.html:300` `.kv-close` |
| Шестерня → Settings | 40×40 | `profile.html:31` `.edit-gear` |
| Бек у Settings | 40×40 | `settings.html:25` `.set-back` |
| Бек у conversation | ~24px гліф, паддінг 0/2/6 | `conversation.html:22-23` `.back` |
| Стрічкові дії фіду | 58×58 ✅ | `feed.html:107` `.act` (але не рендеряться) |
| Таб-бар пункти | висота 64, flex-ширина ✅ | `theme.css:159-172` |

**Оцінка:** таб-бар і основні кнопки — ОК. Але **всі «закрити» = 34px** і всі бек/шестерні = 40px —
нижче за WCAG 2.5.5 / Apple HIG 44pt. На холодному мобільному трафіку промахи по «✕» = роздратування
на кожній overlay (а їх багато: пейвол, лайкери, звіт, why, consent, interview, edit).
**Фікс:** підняти tap-area до 44 через `padding`/невидиму hit-зону, не чіпаючи візуальний кружечок.

**Фікс (~15 хв):** на числовому кроці ставити `input.setAttribute('inputmode','numeric')` і знімати

## 5. Дабл-сабміт та ідемпотентність

**Добре (guard-и є):**
- Свайп фіду: `cand.__done` + `busy` (`feed.html:540-556`).
- Пейвол-депозит/покупка: `busy` (`paywall.js:210,252,300`).
- Depth-submit: `btn.disabled=true` (`profile.html:1313`).
- Reveal/likes-pass лайкерів: `el.disabled/passBtn.disabled` (`matches.html:463,485`).
- Надсилання повідомлення: `sendBtn.disabled=true` + миттєве очищення інпута (`conversation.html:325`).

### 🟡 UX-5 (P3, баг) — match.html: подвійні слухачі через render() ×2

**Пруф:** `match.html` малює двічі — з кешу і зі свіжого `/api/me`:
`match.html:334-337` (`pick(cached)`) і `:343-348` (`pick(me)`) → обидва звуть `render()`.
Усередині `render()` навішуються обробники **щоразу**:
- `match.html:258` `w.addEventListener('click', ... conversation)` — кнопка «Написати»;
- `match.html:265` `why.addEventListener('click', ... openWhyFactor)` — «Чому ми підходимо».

`openWhyFactor()` щоразу створює **нову** overlay і чіпляє її в `body` (`match.html:352-362`). Отже
після двох `render()` один тап по «Чому підходимо» відкриває **дві** overlay поверх одна одної; «Написати»
двічі виконує навігацію. Дизайн-баг, не критичний, але помітний саме на швидкому кеші.
**Фікс:** навішувати обробники один раз (поза `render()`), або гардити прапорцем `bound`.

### 🟡 UX-6 (P3) — profile: edit-форма не блокує кнопку «Зберегти»

**Пруф:** `profile.html:972` submit-хендлер не робить `disabled` на сабміт-кнопці, лише пише
`saveNote='saving'`. Подвійний тап шле `POST /api/profile-info` двічі. Шкода мінімальна (сервер
перезаписує ідемпотентно), але за консистентністю з рештою — треба disable.

### 🟡 UX-9 (P3) — тиха помилка надсилання
`conversation.html:329-331`: при фейлі текст повертається в поле без жодного індикатора. Додати
короткий toast/`showAlert` «не надіслалось».

## 7. Адаптивність / safe-area / клавіатура

**Добре.** `viewport-fit=cover` + `env(safe-area-inset-*)` скрізь; таб-бар піднято над інсетом
(`theme.css:161`). Reduced-transparency/contrast fallback-и (`theme.css:207-213`). max-width на
контейнерах (420–460) → на планшеті 768/1024/1440 контент не розтягується у полотно.

### ⚠️ Клавіатура перекриває інпут — асиметрія
Kink-інтерв'ю має ретельне keyboard-handling через `visualViewport` (`profile.html:1196-1214`), а
**основний композер onboarding/conversation — ні**. Textarea там просто у `.composer` внизу; на iOS
клавіатура може перекрити поле/кнопку відправки. Всередині Telegram WebApp `expand()` частково рятує,
але на малих екранах (320–375) це ризик.
**НЕ ЗМІГ ПЕРЕВІРИТИ:** реальне перекриття на iOS Safari/Telegram — потрібен пристрій або емулятор з
клавіатурою. **Як перевірити:** відкрити onboarding на iPhone SE (320/375), сфокусувати textarea,
переконатись що кнопка ➤ і поле лишаються видимі над клавіатурою.
**НЕ ЗМІГ ПЕРЕВІРИТИ:** landscape та великий системний шрифт (Dynamic Type) — рендер потрібен.

## 8. Доступність (WCAG 2.1 AA)

**Сильні місця:** широке покриття `aria-label`/`data-i18n-aria` (навігація, кнопки, close), `alt` на
контентних фото (`match.html:147`), декоративні фони `aria-hidden`, три незалежні a11y-сигнали в CSS
(`theme.css:207-216`), reduced-motion вимикає всі анімації.

**Прогалини (P3):**
- Focus-trap відсутній у динамічних overlay (розділ 6).
- Контраст: `--hint`/`--muted`/`--faint` на скляних фонах — багато дрібного сірого 10.5–12px
  (напр. `matches.html:38` `.scr-sub`, `feed.html:83` `.lbl` 6.5px UPPERCASE). Дуже дрібний текст +
  низький контраст = ризик провалу 4.5:1. **НЕ ЗМІГ ПЕРЕВІРИТИ** точні співвідношення без рендера
  токенів `theme.css`. **Як перевірити:** прогнати ключові пари `--hint/--muted` на `--surface` у
  світлій і темній темі через контраст-чекер (ціль AA 4.5:1, для <18px).
- Порядок для скрін-рідера в фіді: swipe-only колода без кнопок-альтернатив — керування жестом
  недоступне з клавіатури/AT (`feed.html:615` «No action buttons»). Тап по ринзі є, але like/nope —
  лише драг. Для AT це глухий кут.

## 9. Перформанс UX (LCP / CLS / джанк / картинки)

**Добре.**
- Фото стискаються клієнтом до 1024px, JPEG 0.82 перед аплоадом (`onboarding.html:548-554`,
  `profile.html:1018-1024`) — не тягнуть мегабайтні оригінали.
- Контейнери зображень мають фіксовані розміри (`row-ava` 62px, картка фото 60% висоти,
  `story-avatar` 108px) → мінімальний CLS від фото.
- Фід тримає в DOM лише 2 картки (`feed.html:485-492`) — фактично віртуалізація колоди.

**Дрібне (P3):**
- `<link rel="preconnect" href="https://fonts.gstatic.com">` є на більшості сторінок
  (`matches.html:7`, `feed.html:7` тощо), але **жодного** підключення вебшрифта немає — `font-family`
  просто `'Inter', -apple-system...` (`theme.css:71`) з системним фолбеком. Preconnect **мертвий**
  (нічого не вантажиться) — прибрати, або справді хостити Inter. Плюс: раз Inter не вантажиться,
  типографіка залежить від того, чи є Inter у системі — на Android його зазвичай нема → рендер іншим
  шрифтом (не CLS, але неконсистентність макета між пристроями).
- Списки `matches`/`chat`/лайкери рендеряться повністю без віртуалізації, але через `MIN_SCORE=6` і
  природний cap метчів їхня довжина мала — не проблема на старті.

## 11. Trust-проблема, що виглядає як UI, але б'є по довірі

### 🟡 UX-7 (P2) — тумблери Settings нічого не роблять

**Пруф:** `settings.html:208-227` — `showMe`, `incognito`, `readReceipts`, `notifMatch`, `notifMsg`
зберігаються **тільки** в `localStorage('sixtio_settings')`, на сервер не йде жоден запит. А
`set_age_range_val` «±10 років» і `set_distance_val` «Без обмежень» — взагалі **статичний текст**
(`settings.html:104,108`), без керування.

**Чому це UX/довіра, а не лише функціонал:** холодний юзер вимикає «Показувати мене» або вмикає
«Інкогніто», бачить, як тумблер клацає й запам'ятовується між сесіями — і **вважає, що він
прихований**. Насправді сервер про це не знає, юзер далі у видачі. Це гірше за відсутність тумблера:
це обіцянка приватності, якої немає. (Перетинається з Phase 4 NO-OP-1, але тут — саме як шкода
довірі під рекламу.)
**Фікс:** або зашити ці стани у `/api/me`/`profile-info` (потребує серверної логіки видачі), або
чесно прибрати/позначити «скоро». Найгірший варіант — лишити як є під платний трафік.

## 12. Growth-прапорець (не баг — рішення монетизації)

**UX-10:** для **безкоштовного чоловіка** уся стрічка фото — заблюрена
(`feed.html:378` `img.blurred`, `theme.css`-незалежний `blur(9px)` у `feed.html:34`). Тобто перше
враження чоловіка з реклами — матове скло замість людей. Це навмисна gender-biased монетизація
(підтверджено в CLAUDE.md), але з погляду CR холодного трафіку це агресивно: блюр **до** будь-якої
цінності може рубати top-of-funnel у чоловіків. Рекомендація growth: A/B — показати 1–2 різкі фото
перед блюром, або блюрити з N-ї картки. Рішення за продуктом; фіксом не вважаю.
